# FlowPay — Database Design

Database: PostgreSQL  
Schema owner: Flyway  
JPA schema mode: `validate`

This document describes the target MVP schema. Migrations are introduced incrementally by phase.

## 1. General persistence conventions

### Internal IDs

```sql
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

Internal IDs are used for database joins and foreign keys.

They are never exposed through public APIs.

### Public IDs

Public resources use prefixed ULID-based identifiers.

Examples:

| Resource | Prefix |
|---|---|
| User | `usr_` |
| Merchant | `mrc_` |
| API Key | `key_` |
| PaymentIntent | `pi_` |
| PaymentTransaction | `ptxn_` |
| Refund | `re_` |
| LedgerAccount | `la_` |
| LedgerTransaction | `ltxn_` |
| WebhookEndpoint | `wep_` |
| WebhookEvent | `evt_` |

### Money

```sql
amount_minor BIGINT
currency CHAR(3)
```

Financial amounts are integer minor units.

### Timestamp

Use:

```sql
TIMESTAMPTZ
```

### Enums

Persist Java/domain enums as textual `VARCHAR` values.

Do not use PostgreSQL enum types in MVP migrations.

### Deletes

Financial/business history is not physically deleted as part of normal lifecycle.

Avoid `ON DELETE CASCADE` for core business records.

## 2. Phase 1 tables

### `users`

```text
id              BIGINT PK
public_id       VARCHAR NOT NULL UNIQUE
email           VARCHAR NOT NULL
password_hash   VARCHAR NOT NULL
first_name      VARCHAR NOT NULL
last_name       VARCHAR NOT NULL
status          VARCHAR NOT NULL
created_at      TIMESTAMPTZ NOT NULL
updated_at      TIMESTAMPTZ NOT NULL
version         BIGINT NOT NULL DEFAULT 0
```

User status:

- `ACTIVE`
- `LOCKED`
- `DISABLED`

MVP does not use `PENDING_VERIFICATION`.

Application stores normalized lowercase email.

Database protection:

```sql
CREATE UNIQUE INDEX ux_users_email_lower
ON users (lower(email));
```

Do not rely only on an application duplicate check.

### `merchants`

```text
id              BIGINT PK
public_id       VARCHAR NOT NULL UNIQUE
name            VARCHAR NOT NULL
status          VARCHAR NOT NULL
created_at      TIMESTAMPTZ NOT NULL
updated_at      TIMESTAMPTZ NOT NULL
version         BIGINT NOT NULL DEFAULT 0
```

Status:

- `ACTIVE`
- `SUSPENDED`
- `CLOSED`

### `merchant_members`

```text
merchant_id     BIGINT NOT NULL FK -> merchants.id
user_id         BIGINT NOT NULL FK -> users.id
role            VARCHAR NOT NULL
created_at      TIMESTAMPTZ NOT NULL

PRIMARY KEY (merchant_id, user_id)
```

Roles prepared by schema/domain:

- `OWNER`
- `ADMIN`
- `DEVELOPER`
- `FINANCE`
- `VIEWER`

Indexes:

```sql
CREATE INDEX ix_merchant_members_user
ON merchant_members(user_id);
```

### `merchant_api_keys`

```text
id              BIGINT PK
public_id       VARCHAR NOT NULL UNIQUE
merchant_id     BIGINT NOT NULL FK -> merchants.id
name            VARCHAR NOT NULL
key_prefix      VARCHAR NOT NULL
key_hash        VARCHAR NOT NULL
status          VARCHAR NOT NULL
last_used_at    TIMESTAMPTZ NULL
expires_at      TIMESTAMPTZ NULL
revoked_at      TIMESTAMPTZ NULL
created_at      TIMESTAMPTZ NOT NULL
```

Status:

- `ACTIVE`
- `REVOKED`

Constraints/indexes:

```sql
UNIQUE(key_prefix)

INDEX(merchant_id, status)
```

`key_hash` stores SHA-256 digest of the complete high-entropy API key.

Raw API key is never stored.

### `refresh_tokens`

```text
id                  BIGINT PK
user_id             BIGINT NOT NULL FK -> users.id
token_hash          VARCHAR NOT NULL UNIQUE
expires_at          TIMESTAMPTZ NOT NULL
revoked_at          TIMESTAMPTZ NULL
created_at          TIMESTAMPTZ NOT NULL
last_used_at        TIMESTAMPTZ NULL
replaced_by_id      BIGINT NULL FK -> refresh_tokens.id
```

Indexes:

```sql
INDEX(user_id)
UNIQUE(token_hash)
INDEX(expires_at)
```

`token_hash` stores a SHA-256 digest of the raw opaque token.

Raw refresh token is never persisted.

Rotation must atomically consume/revoke the current token and create its replacement. The implementation must prevent concurrent refreshes from producing multiple valid replacement chains.

## 3. Payment tables

### `payment_intents`

```text
id                       BIGINT PK
public_id                VARCHAR NOT NULL UNIQUE
merchant_id              BIGINT NOT NULL FK -> merchants.id
merchant_order_id        VARCHAR NULL
description              VARCHAR NULL
amount_minor             BIGINT NOT NULL
currency                 CHAR(3) NOT NULL
status                   VARCHAR NOT NULL
refunded_amount_minor    BIGINT NOT NULL DEFAULT 0
refund_reserved_minor    BIGINT NOT NULL DEFAULT 0
created_at               TIMESTAMPTZ NOT NULL
updated_at               TIMESTAMPTZ NOT NULL
version                  BIGINT NOT NULL DEFAULT 0
```

Constraints:

```sql
CHECK (amount_minor > 0)

CHECK (
  refunded_amount_minor >= 0
  AND refund_reserved_minor >= 0
  AND refunded_amount_minor + refund_reserved_minor <= amount_minor
)
```

Indexes:

```text
UNIQUE(public_id)
INDEX(merchant_id, created_at DESC)
INDEX(merchant_id, status, created_at DESC)
INDEX(merchant_id, merchant_order_id)
```

`merchant_order_id` is not an idempotency key and is not globally unique.

### `payment_transactions`

```text
id                        BIGINT PK
public_id                 VARCHAR NOT NULL UNIQUE
payment_intent_id         BIGINT NOT NULL FK -> payment_intents.id
attempt_no                INTEGER NOT NULL
provider                  VARCHAR NOT NULL
provider_transaction_id   VARCHAR NULL
status                    VARCHAR NOT NULL
failure_code              VARCHAR NULL
failure_message           VARCHAR NULL
started_at                TIMESTAMPTZ NULL
completed_at              TIMESTAMPTZ NULL
created_at                TIMESTAMPTZ NOT NULL
updated_at                TIMESTAMPTZ NOT NULL
version                   BIGINT NOT NULL DEFAULT 0
```

Constraints:

```sql
CHECK (attempt_no > 0)
UNIQUE(payment_intent_id, attempt_no)
```

Provider reference:

```sql
CREATE UNIQUE INDEX ...
ON payment_transactions(provider, provider_transaction_id)
WHERE provider_transaction_id IS NOT NULL;
```

when provider semantics guarantee uniqueness.

## 4. Idempotency

### `idempotency_records`

```text
id                     BIGINT PK
merchant_id            BIGINT NOT NULL FK -> merchants.id
operation              VARCHAR NOT NULL
idempotency_key        VARCHAR(255) NOT NULL
request_hash           CHAR(64) NOT NULL
status                 VARCHAR NOT NULL
resource_type          VARCHAR NULL
resource_public_id     VARCHAR NULL
http_status            INTEGER NULL
response_payload       JSONB NULL
created_at             TIMESTAMPTZ NOT NULL
completed_at           TIMESTAMPTZ NULL
expires_at             TIMESTAMPTZ NOT NULL
```

Status:

- `PROCESSING`
- `COMPLETED`
- `FAILED`

Phase 3 actively uses only `PROCESSING` and `COMPLETED`. `FAILED` is reserved for
future explicitly approved recovery semantics and must not be produced by Phase
3 application code.

Phase 3 operations:

- `PAYMENT_INTENT_CREATE`
- `PAYMENT_INTENT_CONFIRM`

`request_hash` stores exactly 64 lowercase hexadecimal SHA-256 characters.

Core uniqueness:

```sql
UNIQUE(merchant_id, operation, idempotency_key)
```

This database constraint is the final protection against concurrent duplicates.

Cleanup index:

```sql
INDEX(status, expires_at)
```

The merchant foreign key does not use `ON DELETE CASCADE`. Expired cleanup is
limited to bounded batches of `COMPLETED` records; `PROCESSING` records are not
deleted by retention cleanup.

```sql

```


## 6. Ledger

### `ledger_accounts`

```text
id                  BIGINT PK
public_id           VARCHAR NOT NULL UNIQUE
account_code        VARCHAR NOT NULL UNIQUE
account_type        VARCHAR NOT NULL
owner_type          VARCHAR NULL
owner_id            BIGINT NULL
currency            CHAR(3) NOT NULL
status              VARCHAR NOT NULL
created_at          TIMESTAMPTZ NOT NULL
```

### `ledger_transactions`

```text
id                  BIGINT PK
public_id           VARCHAR NOT NULL UNIQUE
posting_type        VARCHAR NOT NULL
reference_type      VARCHAR NOT NULL
reference_id        VARCHAR NOT NULL
currency            CHAR(3) NOT NULL
description         VARCHAR NULL
occurred_at         TIMESTAMPTZ NOT NULL
created_at          TIMESTAMPTZ NOT NULL
```

Duplicate-posting protection:

```sql
UNIQUE(posting_type, reference_type, reference_id)
```

### `ledger_entries`

```text
id                      BIGINT PK
ledger_transaction_id   BIGINT NOT NULL FK -> ledger_transactions.id
ledger_account_id       BIGINT NOT NULL FK -> ledger_accounts.id
entry_no                INTEGER NOT NULL
direction               VARCHAR NOT NULL
amount_minor            BIGINT NOT NULL
created_at              TIMESTAMPTZ NOT NULL
```

Constraints:

```sql
CHECK (amount_minor > 0)
CHECK (direction IN ('DEBIT', 'CREDIT'))
UNIQUE(ledger_transaction_id, entry_no)
```

The cross-row debit/credit balance invariant is enforced in domain/application logic and tests in MVP.

## 9. Optimistic locking

Mutable aggregates that need concurrency detection include:

- Merchant
- PaymentIntent
- PaymentTransaction
- Refund
- WebhookEndpoint
- WebhookDelivery

They use a `version` field.

Immutable append-only records such as LedgerTransaction, LedgerEntry, and WebhookEvent do not require optimistic locking for business mutation.
